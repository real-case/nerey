# 0036. Conventional Commits as the commit contract

## Context and Problem Statement

Nerey publishes three packages from one repository, versioned independently (ADR 0002), under a semantic-versioning contract whose MAJOR triggers are unusually broad (ADR 0029). Two things therefore have to be derivable from history rather than reconstructed by memory at release time: which package a change affects, and whether the change is breaking.

With freeform commit subjects, both are a judgement call made weeks later by reading a diff. `git log` between two tags of `@nerey/theme` contains commits touching `@nerey/core`, the Storybook workbench, the ADR corpus and CI, with nothing to filter on but paths — and paths lie, because a change to a core type can be a breaking change for theme consumers while touching no file under `packages/theme/`. Release notes end up hand-written from a diff, which is slow and, more importantly, systematically omits the changes whose significance was not obvious to the person skimming.

There is also a corpus problem. ADR 0001 makes decisions citable by permanent number, but a citation is only useful if it appears where someone will hit it — and the place a future reader lands when asking "why is this line like this" is `git blame`, not the decision index.

## Decision Drivers

* The version bump for each package must be derivable from the commit range, not negotiated at release time.
* Per-package changelogs must be generatable, because hand-curated ones silently drop the entries that matter least to the author and most to a consumer.
* The declaration of "this is breaking" must be machine-readable, since ADR 0029 defines three separate surfaces on which a break can occur and two of them (styling attributes, token names) produce no type error.
* Commit metadata must connect a change back to the record that authorised it, so `git blame` reaches the reasoning in one hop.
* Whatever the contract is, it must be enforced mechanically. An unenforced commit convention decays to roughly compliant, which is not enough to compute a bump from.
* The overhead must suit a repository maintained by one person with three packages, not a fifty-package org monorepo.

## Considered Options

* Conventional Commits 1.0.0 with a scope vocabulary derived from the workspace list
* Freeform subjects with a hand-written `CHANGELOG.md` per package
* Changesets — a per-change markdown file declaring the affected packages and their bump level

## Decision Outcome

Chosen option: "Conventional Commits 1.0.0 with a scope vocabulary derived from the workspace list", because the commit message is written on every change anyway, so putting the contract there adds no artifact and cannot be forgotten separately from the work; and because ADR 0029's `check:public-api` gate gives an independent mechanical verification of the bump, which removes the main reason to prefer an explicitly authored declaration.

The contract:

* Format is `type(scope): subject`, with an optional body and footers, per Conventional Commits 1.0.0.
* Types: `feat`, `fix`, `perf`, `refactor`, `test`, `docs`, `build`, `ci`, `chore`, `revert`.
* Scopes are **derived, not hand-listed**: the allowed set is the unscoped names of the `workspaces` globs in the root `package.json` — `core`, `theme`, `eslint-config` — plus three fixed non-package scopes, `storybook`, `docs` and `repo`. Deriving them means adding a fourth package cannot leave the scope vocabulary stale.
* Version mapping, applied per scope: `feat` implies MINOR for that package; `fix` and `perf` imply PATCH; a `!` after the scope or a `BREAKING CHANGE:` footer implies MAJOR, whatever the type. `docs`, `test`, `ci`, `chore` and `build` imply no bump. `refactor` implies no bump and is therefore a claim that the public surface did not move — a claim `check:public-api` independently verifies.
* While the packages are pre-1.0, the same markers apply one level down, per ADR 0029: a breaking change bumps MINOR on a `0.x` version. The `!` marker is still mandatory, because it is what the release gate reads; the shift is in the arithmetic, not in the declaration.
* A change that implements, exercises or knowingly deviates from a decision record carries a `Refs: ADR 0029` footer. The footer uses the same bare `ADR NNNN` form as the corpus itself, so `scripts/check-adr-citations.mjs` resolves commit citations with the same code path it uses for prose.
* Merges are squash merges, so the PR title is the message that lands on the default branch and is what the contract applies to.

### Consequences

* Good, because per-package changelogs are generated by filtering the range on scope, which means an entry cannot be omitted through inattention.
* Good, because `git log --grep` over type and scope answers "what changed in `@nerey/theme` since the last release" precisely, and the `!` marker makes breaking changes greppable rather than requiring a diff read.
* Good, because the bump has two independent signals that must agree — the author's declared type and the mechanical API diff from ADR 0029. Disagreement is a release-gate failure, which is exactly where a mislabelled commit should be caught.
* Good, because `Refs:` footers put decision numbers into `git blame` output, so the path from a puzzling line to its rationale is one lookup.
* Bad, because a wrong type produces a wrong bump for anything the API gate cannot see — a behavioural change in the lifecycle runtime (ADR 0018) or in degradation ordering (ADR 0012) is breaking without altering a single signature. The gate cannot catch it; only care can.
* Bad, because enforcement adds a `commit-msg` hook, which is friction during `--amend` and rebase loops and is bypassable with `--no-verify`. CI re-validates the whole PR range, so a local bypass does not reach the default branch, but it does mean the failure arrives later than the commit.
* Neutral, because the squash-merge rule moves the real enforcement surface to PR titles, so the CI check must validate the title as well as the constituent commits, and the two can legitimately differ.
* Neutral, because the type taxonomy will be applied inconsistently at the margins — `refactor` versus `chore` for a file move is a coin flip. Only `feat`, `fix`, `perf` and `!` carry semantic weight, so marginal misuse is cosmetic.

### Confirmation

`npm run check:commits` (`scripts/check-commits.mjs`), added by this decision:

* Locally it is invoked from a `commit-msg` git hook against the message being written. This is the one enforcement point edit-time hooks cannot cover (ADR 0034), because there is no message until commit time.
* In CI it runs over the full PR commit range plus the PR title, so a `--no-verify` bypass is caught before merge.
* Internally it wraps `commitlint` with `@commitlint/config-conventional`, overriding `scope-enum` with the set computed from `workspaces` in the root `package.json` plus the three fixed non-package scopes. The vocabulary is computed at run time, so it cannot drift from the workspace layout.
* It resolves every `Refs: ADR NNNN` footer against `docs/decisions/`, reusing `scripts/check-adr-citations.mjs`, so a commit cannot cite a record that does not exist.
* Per ADR 0033 it is registered in the gate fixture manifest with planted violators: a subject with no type, a scope outside the derived set, a `BREAKING CHANGE:` footer with no `!` and no bump implication, and a `Refs:` footer citing a nonexistent number. Each must be rejected with its documented message.

The release-time cross-check lives in ADR 0029: `npm run check:public-api` compares the working surface against the last published snapshot, and a removal or rename with no `!` commit in the range fails the release. That is what keeps the commit type honest rather than merely well-formed.

## Pros and Cons of the Options

### Conventional Commits 1.0.0 with a derived scope vocabulary

Structured subjects, `!` and `BREAKING CHANGE:` as the break markers, scope selecting the package.

* Good, because the contract rides on an artifact that already exists on every change, so there is nothing extra to remember and nothing extra to review.
* Good, because it is a published, widely implemented specification with mature tooling for both linting and changelog generation, so neither needs writing.
* Good, because deriving `scope-enum` from `workspaces` removes the most common decay mode of this convention, which is a scope list that stopped matching the repository.
* Good, because the `!` marker is a single greppable token, which is what makes an automated release gate possible at all.
* Neutral, because it adds `commitlint` and a `commit-msg` hook — real but small, and the hook infrastructure is needed for nothing else.
* Bad, because the declaration is made at the moment of least information: the author states the bump while writing the code, not after seeing the assembled release.
* Bad, because it is easy to satisfy formally while getting the semantics wrong, and only the subset of semantics visible to `check:public-api` is verified.

### Freeform subjects with a hand-written `CHANGELOG.md` per package

The traditional approach: write good messages, curate release notes by hand.

* Good, because hand-written release notes are better prose than generated ones — they group related changes and explain migrations, which a generator cannot.
* Good, because it imposes zero tooling, zero hooks and zero vocabulary to learn.
* Good, because it puts no pressure on commit granularity, so commits can be shaped for review rather than for the changelog.
* Neutral, because it works well at low release frequency, where the author still remembers the release's contents.
* Bad, because the bump level is a judgement made from a diff, and the surfaces most likely to break silently — the `data-*` attribute contract from ADR 0020 and the token names from ADR 0024 — are the ones a diff read is worst at surfacing.
* Bad, because a curated changelog omits by construction. The entries that get dropped are the ones the author considered unimportant, which correlates poorly with what consumers considered important.
* Bad, because nothing is machine-readable, so no release gate can exist and ADR 0029 loses its enforcement mechanism.

### Changesets

A markdown file per change declaring affected packages and bump levels, consumed by a release command.

* Good, because the bump is declared explicitly and in prose, which is the most honest possible statement of intent and produces genuinely good changelog entries.
* Good, because it handles multi-package bumps and internal dependency propagation properly, which matters when packages depend on each other.
* Good, because the declaration is reviewable as a file in the PR diff, so a reviewer sees "this is a MAJOR" as a line to approve rather than as a token in a subject.
* Neutral, because it does not replace a commit convention; a repository using it usually still wants readable commit messages, so it is an additional artifact rather than a substitute.
* Bad, because it is a separate file that is easy to forget and, once a bot starts nagging for it, easy to add mechanically without thought. A forgotten changeset silently publishes no version at all.
* Bad, because it duplicates a declaration that would exist in the commit anyway, and the two can disagree, which creates a third thing to reconcile.
* Bad, because its main advantage — an explicit author-stated bump — is largely supplied here by `check:public-api`, which derives the required bump mechanically from three surfaces and does not depend on the author's recall.

## More Information

Specification: <https://www.conventionalcommits.org/en/v1.0.0/>. Linting is `commitlint` with `@commitlint/config-conventional` and a computed `scope-enum`; changelog generation runs over the commit range filtered by scope, per package, at release time.

This record supplies the input that ADR 0029 consumes: the `!` marker and the type are how a release computes its bump, and `check:public-api` is how that computation is audited. ADR 0001 defines the `ADR NNNN` citation form the `Refs:` footer reuses, ADR 0033 requires the commit gate to prove it can reject a malformed message, and ADR 0034 explains why the commit-message check stays a git hook rather than moving to edit time.

Revisit if release cadence rises to the point where hand-reviewing a generated changelog before publishing stops being practical, or if a fourth package introduces cross-package dependency bumps — that is the case Changesets handles natively and this contract handles only by convention.
