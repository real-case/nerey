# 0007. Merged coverage threshold gate

## Context and Problem Statement

ADR 0006 splits the test suite into two Vitest projects: `unit` in jsdom for contract logic, and
`storybook` in a real browser for anything with a rendered surface. That split makes per-project
coverage meaningless as a gate. A themed component is exercised only by its stories, so the `unit`
project reports it at zero; the lifecycle rule evaluator is exercised only by unit tests, so the
`storybook` project reports *it* at zero. Thresholds applied per project would therefore either be set
low enough to pass on both — measuring nothing — or force a jsdom duplicate of every story purely to
move a number, which is exactly the duplication ADR 0006 eliminated.

The second question is what the threshold is for. Nerey's real specification is its acceptance
criteria: the four degradation steps, exact `type@version` resolution, lifecycle expiry driving
`readonly`, persistence rollback leaving a widget locked. Those are asserted directly and coverage adds
nothing to them. What coverage catches is the different failure: a module that arrived with no tests at
all and nobody noticed, because the diff was large and the reviewer was reading the interesting part.

## Decision Drivers

* Coverage must be computed once, across both projects, or it penalises the test topology rather than
  measuring it.
* The gate must fail the build. An advisory percentage printed at the end of a green run changes no
  behaviour.
* The number must be high enough that an untested module is visible, and low enough that nobody writes
  a test to satisfy the arithmetic.
* Exclusions must be enumerated with reasons, in version control, because an unexplained exclusion is
  indistinguishable from hiding something.
* The threshold itself must be a reviewable diff, not a CI flag someone can pass on one branch.

## Considered Options

* A single merged threshold of 80% across both projects
* Per-project thresholds tuned separately (for example `unit` at 90%, `storybook` at 60%)
* Per-file thresholds, or a diff-coverage gate on changed lines only

## Decision Outcome

Chosen option: "A single merged threshold of 80% across both projects", because it is the only
formulation that measures the code rather than the environment it happens to be tested in, and because
80% is the level at which an entirely untested module fails the build while a well-tested one is never
short of a few lines of unreachable defensive code.

Concretely: `npm run test:coverage` runs `vitest run --coverage` at the workspace root, so both
projects execute in one invocation and the V8 provider accumulates into one report. `coverage.thresholds`
is set in the root Vitest config — committed, not passed on the command line — to 80 for `lines`,
`statements`, `functions` and `branches`, applied globally to the merged report, with
`thresholds.autoUpdate` off so the number can never be silently ratcheted down by a tool. Reporters are
`text` for the console, `lcov` for CI annotation, and `json-summary` so the gate script can read the
totals.

**Excluded, with reasons:**

* `**/*.stories.tsx` — stories are the test inputs in the `storybook` project, not subjects. Counting
  them as covered source measures the suite against itself.
* `**/*.types.ts` and `**/*.d.ts` — type-only modules erase to nothing; they contribute no executable
  statements and only distort the denominator.
* `packages/theme/src/tokens.generated.ts` and `**/*.module.css.d.ts` — generated by
  `npm run gen:tokens` and `npm run gen:css-types`, and verified for correctness by
  `npm run check:tokens`. Their correctness question is "does it match the source of truth", which
  coverage cannot answer.
* `scripts/**` — the gate scripts. They are verified by ADR 0033's discipline of rejecting a planted
  violator, which is a stronger statement than line coverage: a gate can be fully covered and still
  fail to reject anything.
* `.storybook/**`, `**/*.config.ts` and `**/__fixtures__/**` — configuration and test data.

**Deliberately not excluded:**

* `packages/core/src/mock/**` — the dev and fixture layer is shipped surface (FR-37) with its own
  acceptance criterion (AC-21). Excluding it would be excluding a published module because it is
  inconvenient.
* The degradation and error paths. They are the branches most likely to be silently broken and the
  ones the branch metric is actually good at.
* `packages/theme` components. They are covered through the `storybook` project, which is the entire
  reason the merge exists.

### Consequences

* Good, because a component covered only by stories and a module covered only by unit tests both count,
  so the metric stops arguing with the test topology.
* Good, because the branch threshold puts pressure exactly where Nerey's complexity is — the four-step
  degradation chain, expiry-rule evaluation, and version-resolution misses are all branch-shaped.
* Good, because the threshold lives in the committed config, so lowering it is a diff someone has to
  defend in review.
* Bad, because a global average can hide a new untested file behind a large well-tested one. This is
  the real weakness of the choice and it is why per-file coverage is recorded below as a probable later
  addition rather than dismissed.
* Bad, because merged coverage requires running both projects, so the number is only available from the
  slow full run — a contributor working with `npm run test:unit` will see a misleadingly low figure if
  they ask for coverage there.
* Neutral, because 80% is a floor and not a target; a module can pass it and still be untested for the
  behaviour that matters, which is why the acceptance criteria and the conformance kit (ADR 0006), not
  this gate, are the actual specification.

### Confirmation

* `npm run test:coverage` — the gate itself. Vitest exits non-zero when any of the four merged metrics
  falls below 80. It is wired into CI as a required check with no `|| true`, no `continue-on-error`, and
  no separate "coverage" job that is allowed to fail.
* Thresholds are declared in the root Vitest config and committed; CI passes no coverage flags, so the
  gate cannot be weakened per branch or per workflow.
* The exclusion list lives in the same config with the reasons above kept beside it, so adding an
  exclusion is a reviewable change rather than an invisible one.
* `npm run check:gates` — per ADR 0033, the coverage gate is itself proven: the run adds an untested
  module to a scratch tree and asserts a non-zero exit, so a misconfiguration that silently stops
  enforcing thresholds is caught rather than enjoyed.

## Pros and Cons of the Options

### A single merged threshold of 80% across both projects

* Good, because it measures a module once, no matter which project exercises it.
* Good, because it is a single number in a single committed file — trivial to reason about, hard to
  quietly subvert.
* Good, because it leaves headroom for genuinely unreachable code (exhaustive `switch` defaults, type
  guards on impossible states) without inviting tests written for the compiler.
* Neutral, because 80 is a convention rather than a derived figure; its justification is that it is
  high enough to fail on an untested module and low enough not to reward coverage theatre.
* Bad, because the average can mask a single untested new file.

### Per-project thresholds tuned separately (for example `unit` at 90%, `storybook` at 60%)

* Good, because each project's number is available from a faster, narrower run.
* Good, because it would show at a glance which half of the suite is thin.
* Bad, because it reintroduces exactly the accounting problem the two-project split removed: a themed
  component drags the `unit` number down for being tested correctly in the other project.
* Bad, because it creates an incentive to write a jsdom duplicate of a story to lift the `unit`
  percentage — the specific waste ADR 0006 was designed to prevent.
* Bad, because the two numbers have to be tuned against each other whenever a module moves between
  being story-covered and unit-covered, which is normal churn.

### Per-file thresholds, or a diff-coverage gate on changed lines only

* Good, because it catches the one case the global average hides: a new file with no tests.
* Good, because a diff-coverage gate scales naturally — it never asks anyone to retroactively cover
  code they did not touch.
* Neutral, because it is compatible with the chosen option; it is an addition, not a replacement.
* Bad, because per-file attribution is least reliable exactly where this repository is unusual: a file
  executed only through a story in the browser project, or through a portable story composed into a
  unit test, is the case where the merged report's file mapping is hardest to trust.
* Bad, because it fails on files that legitimately have no branches to cover — a subpath entry module
  that only re-exports (ADR 0028), or a `'use client'` shim — producing exemption lists that grow until
  the gate is noise.
* Bad, because a diff-coverage gate needs a base ref and a CI-specific integration, making it a
  pull-request-only signal that cannot be reproduced locally with one command.

## More Information

The two-project topology this gate merges over is ADR 0006, and the workbench whose stories supply half
the coverage is ADR 0031. The self-test requirement applied to this gate — a gate must be observed
rejecting a planted violator before it is trusted — is ADR 0033, and edit-time enforcement of the
cheaper checks is ADR 0034.

Revisit by adding per-file or diff coverage as a *second* gate once the merged number has been stable
for a few releases and the file attribution from the browser project has been spot-checked against
known-covered modules. Revisit the 80 figure only downward with an explicit reason recorded here, or
upward once the conformance kit covers both built-in widgets and the number is being exceeded without
effort.
